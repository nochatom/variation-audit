## 2026-07-26 - [Database Count Optimization in Billing Service]
**Learning:** In SQLAlchemy/PostgreSQL applications, loading matching rows or IDs into memory (`len(session.execute(select(Model.id)...).scalars().all())`) just to count them wastes network payload and application memory. Replacing it with a database-side count (`select(func.count(Model.id))`) eliminates that transfer and materialization: the application receives a single scalar instead of N rows, so the client-side cost drops from $O(N)$ to $O(1)$. The database still scans the same rows to satisfy the predicate — this is not an $O(1)$ database operation and does not necessarily reduce database CPU.
**Action:** Prefer `select(func.count(...))` over fetching rows/scalars and taking `len()` in Python whenever the count is all you need, so rows are never loaded into Python. It does not make the underlying scan cheaper; if the count query itself is slow, address that separately with indexing or an approximate/maintained count.

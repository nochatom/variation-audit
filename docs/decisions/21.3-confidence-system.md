# Decision: Confidence System (.21.3)

> Task: `variation-audit-z3x.21.3` · Parent: `.21` · Status: **accepted** (2026-06-27)
> Extends [engine-product-api-contract-v1](../engine-product-api-contract-v1.md). Defines scoring semantics so confidence is rendered consistently everywhere.

## 1. Problem
Contract v1 carried two confidence representations with no defined relationship:
- `variation.confidence_score` — float `0.0–1.0`
- `estimated_value.confidence` — `low | medium | high`

Ambiguity: are they the same thing in two formats? What thresholds turn a score into a band? Without rules, the product UI would invent its own.

## 2. Decision — Two Orthogonal Axes
Confidence is split into **two independent axes** with distinct meaning:

| Axis | Field | Type | Question it answers |
|------|-------|------|---------------------|
| **Detection** | `confidence_score` | float 0.0–1.0 | How sure is the engine this *is* a legitimate unclaimed variation? |
| **Valuation** | `estimated_value.confidence` | low/med/high | How sure is the engine of the *dollar estimate*? |

These are independent: a variation can be near-certain (`confidence_score: 0.95`) while its value is a rough guess (`valuation: low`), and vice versa.

## 3. Canonical Score → Band Mapping (single source of truth)
One mapping converts any 0.0–1.0 score to a band. The product layer **must not** re-implement thresholds.

| band | range |
|------|-------|
| `low` | 0.00 – 0.49 |
| `medium` | 0.50 – 0.79 |
| `high` | 0.80 – 1.00 |

(Ranges are inclusive of the lower bound; `high` includes 1.0.)

## 4. Derived Fields
- Each variation gains `confidence_band` (`low|medium|high`), **derived by the engine** from `confidence_score` via §3. The UI displays the band; the score is available for sorting/detail.
- `estimated_value` gains an optional numeric `valuation_confidence_score` (0.0–1.0). When present, `estimated_value.confidence` is derived from it via the **same** §3 mapping, keeping both axes on one scale.

### Updated shapes
```json
"confidence_score": 0.0,
"confidence_band": "low | medium | high",
"estimated_value": {
  "amount": 0,
  "currency": "AUD",
  "valuation_confidence_score": 0.0,
  "confidence": "low | medium | high"
}
```

## 5. Relationship to `status` (orthogonal, not derived from confidence)
`variation.status` (`detected | confirmed | uncertain`) is **workflow/assessment state**, not a confidence band:
- `detected` — engine's default output for a candidate variation.
- `uncertain` — engine flags it as needing human attention (typically, but not necessarily, `confidence_band: low`).
- `confirmed` — set by a human in the commercial review workflow (`.14`), never by the engine.

Confidence informs review prioritisation; it does not set `status`. Keeping them separate avoids conflating "the model is unsure" with "a human approved it".

## 6. Scope
- Thresholds (0.49 / 0.79) are part of `contract_version: v1`; changing them is a contract change so historical results stay interpretable.
- One shared mapping definition used by engine + product (generated/imported, not duplicated).

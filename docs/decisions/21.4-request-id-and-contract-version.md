# Decision: request_id + contract_version (.21.4)

> Task: `variation-audit-z3x.21.4` · Parent: `.21` · Status: **accepted** (2026-06-27)
> Extends [engine-product-api-contract-v1](../engine-product-api-contract-v1.md). Reliability/idempotency layer beneath all engine calls.

## 1. Decision
Every engine request carries two new envelope fields: **`request_id`** (idempotency + tracing) and **`contract_version`** (schema negotiation). The engine already returns `engine_version`; these complete the request/response provenance.

## 2. Updated Input Envelope
```json
{
  "request_id": "uuid-v4",
  "contract_version": "v1",
  "project_id": "string",
  "company_id": "string",
  "project_type": "construction_trade",
  "country": "AU",
  "documents": [ "...as contract v1..." ],
  "callback_url": null
}
```
Both fields are **required** on `POST /v1/analyses`. They are echoed on every job poll response and on every error envelope.

## 3. request_id — Idempotency Key
- **Client-generated UUID v4**, unique per logical submission.
- **Dedup window: 7 days.** A repeat `POST` with a `request_id` seen within the window returns the *existing* job (`200`, not a new `202`) — prevents duplicate, double-charged engine runs (e.g. retries after a network blip).
- **Conflict guard:** if the same `request_id` arrives with a *different* request body, reject `409 CONFLICT` (`code=IDEMPOTENCY_KEY_REUSE`). Idempotency keys must not be recycled across distinct payloads.
- **Tracing:** `request_id` is the correlation ID — propagated into engine logs, the `jobs` table, notifications, and all responses. One id ties product UI → job → engine logs → result.
- **Storage:** `jobs` table has a unique index on `request_id` (within the dedup window).

## 4. contract_version — Schema Negotiation
- Identifies the **request/response schema** the product layer is speaking (currently `"v1"`).
- Engine validates it **synchronously at POST**; an unsupported value → `400` (`code=UNSUPPORTED_CONTRACT_VERSION`, with `details.supported: ["v1"]`). No job is created.
- Distinct from `engine_version`:
  - `contract_version` = the product↔engine **API schema** agreement.
  - `engine_version` = the engine **build/model-pipeline** version, for result provenance/reproducibility.
- They version **independently**: the engine internals can advance (`engine_version` bumps) while the contract stays `v1`.

## 5. Error Codes Added
| code | HTTP | when |
|------|------|------|
| `IDEMPOTENCY_KEY_REUSE` | 409 | same `request_id`, different body |
| `UNSUPPORTED_CONTRACT_VERSION` | 400 | `contract_version` not in supported set |
| `INVALID_INPUT` | 400 | missing/malformed `request_id` or `contract_version` |

## 6. Scope
- MVP supports exactly one contract version: `v1`.
- Idempotency dedup window default 7 days (configurable).

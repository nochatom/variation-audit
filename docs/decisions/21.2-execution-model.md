# Decision: Engine Execution Model — Async Job System (.21.2)

> Task: `variation-audit-z3x.21.2` · Parent: `.21` (engine integration) · Relates: blocks `.18` (background jobs)
> Status: **accepted** (2026-06-27, founder-approved with defaults) · Contract: extends [engine-product-api-contract-v1](../engine-product-api-contract-v1.md)
>
> **MVP settings (locked):** polling-only (no webhook) · 15-min job timeout · no cancellation.

## 1. Decision
Adopt an **asynchronous, job-based execution model** as the primary (and for MVP, the only required) way the product layer invokes the engine.

**Why not synchronous:** the engine runs a multi-stage LLM pipeline (ingest → baseline → classify → quantify → confidence) over many documents using `claude-opus-4-8` with adaptive thinking. Per-project runtime is seconds-to-minutes and grows with document count — well beyond a safe HTTP/proxy timeout (30–60s). A synchronous call would time out, hold connections, and give no progress feedback.

**Optional later:** a thin synchronous `POST /v1/quick-check` for a *single* document (<~10s, no cross-document evidence linking) for interactive "is this a variation?" UX. **Not in MVP scope** — listed under Future.

## 2. API Surface

### Create a job
```
POST /v1/analyses
```
Body = Input Schema v1, plus the `.21.4` envelope fields (`request_id`, `contract_version`) and an optional `callback_url`.

Response — `202 Accepted`:
```json
{
  "job_id": "string",
  "status": "queued",
  "request_id": "string",
  "created_at": "ISO8601",
  "links": { "self": "/v1/analyses/{job_id}" }
}
```

### Poll a job
```
GET /v1/analyses/{job_id}
```
Response — `200 OK`:
```json
{
  "job_id": "string",
  "project_id": "string",
  "status": "queued | running | succeeded | failed | canceled",
  "progress": { "stage": "classify", "percent": 0.6 },
  "result": { "...Output Schema v1, present only when status=succeeded..." },
  "error": { "code": "string", "message": "string", "retryable": false },
  "engine_version": "v1",
  "created_at": "ISO8601",
  "updated_at": "ISO8601"
}
```

### Cancel a job — POST-MVP (not implemented for MVP)
```
DELETE /v1/analyses/{job_id}   ->   status: canceled (if not terminal)
```
> Deferred per §10. MVP has no cancellation and no `canceled` state.

### Callback (optional)
If `callback_url` is supplied, the engine `POST`s the full poll payload to it once on reaching a **terminal** state (`succeeded|failed|canceled`). Polling remains the source of truth; the webhook is an optimization. Callbacks are signed (HMAC header) and retried with backoff.

## 3. Status Lifecycle (MVP)
```
queued ──► running ──► succeeded
               │
               └─────► failed      (terminal, may be retryable; incl. 15-min ENGINE_TIMEOUT)
```
- `queued` — accepted, awaiting a worker.
- `running` — a worker is executing the pipeline; `progress.stage` reflects the current engine stage.
- Terminal states (`succeeded`, `failed`) never transition further. A failed+retryable job is re-run by **submitting a new job** (same `request_id` is rejected as duplicate — see idempotency), not by mutating the old one.
- No `canceled` state in MVP (cancellation deferred — see §10).

## 4. Result Delivery
- MVP: result returned **inline** in the poll payload when `status=succeeded`.
- Guardrail: if the serialized result exceeds a size cap (e.g. 1 MB), return `result_url` to a stored artifact instead of inline `result`. (Defer artifact storage until a project actually exceeds the cap.)

## 5. Idempotency, Tracing, Retries  (interlocks with .21.4)
- `request_id` is the **idempotency key**: a repeat `POST` with the same `request_id` returns the *existing* job (`200`, not a new `202`) within a dedup window (e.g. 7 days). Prevents duplicate-charge double-runs.
- `request_id` is echoed on every response and logged across product + engine for tracing.
- **Internal** retries: transient LLM/API errors (429/5xx) are retried inside the worker with exponential backoff; only exhausted transients surface as `failed` with `retryable=true`.
- Clients must **not** auto-resubmit on timeout — they poll; the job is still running.

## 6. Error Envelope
```json
{ "error": { "code": "INVALID_INPUT | ENGINE_TIMEOUT | LLM_UNAVAILABLE | INTERNAL",
             "message": "human readable",
             "retryable": true,
             "details": { } } }
```
Validation failures are caught **synchronously at POST** (`400`, no job created). Processing failures appear on the job as `status=failed`.

## 7. SLAs / Client Guidance
- POST→`202` ack: < 1s (just enqueues).
- Poll cadence: client uses backoff — start 2s, cap 15s. (Or rely on `callback_url`.)
- Soft per-job processing timeout (configurable; e.g. 15 min) → `failed/ENGINE_TIMEOUT`.

## 8. Mapping to .18 (Background Jobs)
This decision **defines the contract** that `.18` implements:
- A durable job queue + a `jobs` table (`job_id`, `request_id`, `status`, `progress`, `result_ref`, `error`, timestamps).
- A worker pool that consumes the queue, runs the reused engine pipeline, writes status transitions, then fires notifications + the optional webhook.
- Queue tech is an `.18`/architecture (`.1`) choice (DB-backed queue is simplest for MVP; Redis/RQ or Celery if scale demands). **Not decided here.**

## 9. Future Extensions
- `POST /v1/quick-check` synchronous single-doc preview.
- Streaming progress via SSE/WebSocket (supersedes polling for live UX).
- Incremental / delta analysis (re-run only new documents) — pairs with contract §7.
- Multi-project batch submission.

## 10. Resolved Decisions (2026-06-27, founder-approved)
1. **Webhook:** ❌ not in MVP — **polling-only**. `callback_url` and the webhook flow move to Future (§9). The product layer polls `GET /v1/analyses/{job_id}` with backoff.
2. **Max processing time:** **15 minutes**, then the job is force-failed with `status=failed`, `error.code=ENGINE_TIMEOUT`, `retryable=true`.
3. **Cancellation:** ❌ not in MVP — drop `DELETE /v1/analyses/{job_id}`. Lifecycle is `queued → running → succeeded | failed` only (no `canceled` state for MVP). Revisit post-MVP.
